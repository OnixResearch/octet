## Context

Octet has the strongest existing evaluator-neutral core, while Mantle has the strongest existing receipt-producing embedded-evaluator shell. Cairn, Trellis, and Animus demonstrate that the same generation and freshness problem recurs outside both products. The extraction therefore must not make Octet or Mantle the runtime dependency for the rest of the stack.

The extraction boundary is the declared export contract, not Nickel evaluation semantics and not product-specific policy validation.

## Decisions

### 1. A standalone repository owns the neutral contract

**Choice:** Create `OnixResearch/nickel-export` with canonical packages named `nickel-export-core` and `nickel-export`. The standalone repository owns export request, manifest, receipt, diagnostic, compatibility, and release-profile schemas.

**Rationale:** Multiple products need the contract without Octet lints, Mantle store/build machinery, Cairn lifecycle behavior, or a sibling checkout. Independent ownership also gives schema compatibility and release cadence one review surface.

### 2. The core is evaluator-neutral and effect-free

**Choice:** `nickel-export-core` accepts plain declared paths, exact source/dependency/output bytes, evaluator descriptors, format/selector/contract metadata, and captured evaluator diagnostics. It performs normalization, validation, BLAKE3 identity construction, deterministic ordering, manifest/receipt construction, and freshness comparison without reading files, spawning `nickel`, inspecting environment state, writing outputs, printing, or consulting clocks.

The core targets `#![no_std]` plus `alloc`; serialization support is feature-gated and deterministic fixtures cover enabled encodings.

**Rationale:** Octet invokes an external `nickel` binary, while Mantle embeds `crunch-eval`. A core tied to either evaluator would recreate the duplication at a different layer.

### 3. The std shell is thin and explicit

**Choice:** The standalone CLI shell owns argument parsing, bounded file reads, explicit dependency collection, external `nickel` invocation, output writes, stdout/stderr, and exit codes. It never discovers undeclared imports silently. If an evaluator reports additional imports, the shell must reject the run or include them explicitly in the observed dependency closure before accepting a receipt.

**Rationale:** Generated-file provenance is unsound if imports can affect output without appearing in identity material.

### 4. Canonical schemas do not silently impersonate legacy schemas

**Choice:** The standalone repository introduces versioned `onix-nickel-export-*` schemas. Octet and Mantle adapters may project canonical records into their existing schema names only through tested compatibility functions. The canonical preimage, field ordering, BLAKE3 algorithm label, and non-claim text are fixture-backed.

**Rationale:** Octet manifests and Mantle receipts currently encode different but overlapping facts. Reusing either schema name for a new semantic union would hide a breaking change.

### 5. Evaluator identity is part of acceptance

**Choice:** Every accepted export records an evaluator descriptor containing an implementation identity, version or immutable package identity, normalized options, selected format, and declared import-path policy. Mixed evaluator identities in one manifest fail unless a versioned profile explicitly permits them.

**Rationale:** Equal source bytes do not establish equal generated bytes across evaluators or option sets. Receipts must state what actually produced the output.

### 6. Cutover is consumer-owned and incremental

**Choice:** Octet is the first dependency cutover because it owns the current reusable core. It pins an immutable standalone revision, delegates neutral operations, and keeps only an explicit compatibility facade. Mantle, Cairn, Trellis, and Animus each require a separate Cairn package in their own repository before changing their evaluator shell or generated artifacts.

A consumer may keep its current implementation until its positive and negative compatibility corpus passes. No workspace-relative path is a release dependency.

**Rationale:** A cross-repository big-bang move would obscure ownership and make failures difficult to attribute.

### 7. Conformance covers both success and failure

**Choice:** The standalone corpus includes stable JSON, TOML, YAML, and raw exports; external and embedded evaluator observations; multiple declared dependencies; selector and contract metadata; and check-mode freshness. Negative fixtures include stale source, dependency, output, evaluator, or command metadata; undeclared dependencies; duplicate output rows; mixed evaluators; unsupported formats or schema versions; path escape; malformed manifests; contract failures; secret-like material; and weakened non-claims.

**Rationale:** The shared value is fail-closed freshness and provenance, not merely a convenience wrapper around `nickel export`.

## Rejected Alternatives

- **Keep the helper in Octet:** unrelated consumers would inherit an evidence/lint product or duplicate the behavior.
- **Use Mantle as the common exporter:** this would couple configuration generation to a build/store product and its embedded evaluator.
- **Extract only a shell script:** it would not provide typed compatibility, embedded-evaluator integration, or deterministic receipt validation.
- **Move every consumer in one change:** this would violate repository ownership and make rollback non-local.

## Risks / Trade-offs

- Canonical schemas add a migration layer before they reduce code.
- Import-closure accuracy depends on evaluator observations; undeclared imports must fail closed rather than be guessed.
- Secret-marker checks are bounded heuristics and must never be described as proving that output is secret-free.
- A standalone release introduces pin-update work, but that cost is preferable to five independently evolving freshness contracts.

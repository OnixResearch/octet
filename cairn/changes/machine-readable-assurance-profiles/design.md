# Design: Machine-readable assurance profiles

## Context

Octet has typed Nickel catalogs for strict Rust profiles, effect closure, proof rails, and external evidence inputs. Those catalogs describe individual rails. They do not describe a component assurance case across independent concern planes.

The root workspace vocabulary defines an assurance profile as required mechanisms, evidence roles, scopes, and non-claims for one component or candidate. A profile declaration is policy input. It is not a passing receipt or release decision.

## Decisions

### Decision: Use a closed linked Nickel profile

**Choice:** Add `standards/policies/assurance-profiles/contracts.ncl`. The profile contains a stable ID, summary, subject scope, assumptions, trusted computing base, mechanisms, evidence requirements, and profile-level non-claims.

Mechanisms reference assumption, trusted-base, and evidence IDs. Cross-field rules reject duplicate IDs, unresolved references, and unreferenced declarations. Assurance-plane values are closed to `construction`, `semantic-design`, `verification`, `effect-control`, and `provenance-readiness`.

**Rationale:** Explicit references prevent a list of controls from looking like cumulative proof. They also make every selected assumption, trusted component, and evidence requirement traceable to a protected property.

### Decision: Keep one profile per generated identity artifact

**Choice:** Author the pilot in `onixos-lifecycle-proof.ncl` and export only that profile to `generated/onixos-lifecycle-proof.json`.

**Rationale:** The generated JSON BLAKE3 remains specific to one profile. Adding another profile does not change the pilot output identity.

### Decision: Reuse the existing Nickel Export identity core

**Choice:** Add an export spec and use `octet-standards nickel-export-manifest` to bind exact source, contract dependency, generated JSON, evaluator identity, command, byte length, and BLAKE3 digests.

**Rationale:** Octet already delegates canonical evaluator-neutral manifest semantics to the pinned `nickel-export-core`. A new profile-specific hashing implementation would create a semantic fork.

### Decision: Make OnixOS the first bounded pilot

**Choice:** The first profile names the active OnixOS lifecycle proof scope and existing evidence paths. It includes the lifecycle Verus source, physical-switch Kani harnesses, canonical Kamacite FSM requirement, Octet conformance, Valence linkage, and Cairn ingestion.

The profile marks each artifact as required. It does not report completion. An OnixOS pin update remains a separate consumer-owned change after Octet publishes the profile.

**Rationale:** OnixOS already has independent mechanisms with explicit gaps. It exercises every assurance plane without inventing a new proof claim.

### Decision: Preserve runtime and ownership boundaries

**Choice:** Profile evaluation and generation stay in explicit Nickel/Nix tooling. Ordinary Octet runtime checks do not evaluate the profile. Valence continues to own evidence identity and linkage semantics. Cairn continues to own candidate readiness.

**Rationale:** A declaration cannot silently become runtime authority, proof evidence, or release eligibility.

## Validation design

Positive fixtures prove a complete minimal profile and the full OnixOS pilot export. Negative fixtures reject:

- empty profile or mechanism non-claims;
- duplicate mechanism, assumption, trusted-base, or evidence IDs;
- unresolved mechanism references;
- declarations that no mechanism references;
- unsupported assurance planes;
- unknown fields or malformed subject scope.

The focused Nix check regenerates JSON, compares exact bytes, regenerates the BLAKE3 manifest, validates fixtures, and checks the package layout. Policy validation confirms family registration.

## Risks and trade-offs

- The OnixOS profile can drift as its active proof change evolves. Exact paths and validation commands make that drift reviewable.
- Nickel validates declared shape and references, not whether a command later passes.
- The first release has one profile and no generic runtime selector. This keeps the pilot bounded and avoids another CLI surface before consumer evidence exists.
- Cross-repository adoption remains blocked until a committed Octet revision is published and selected by OnixOS.

## Claim boundary

A passing profile check proves only that the declaration conforms to the selected schema, cross-reference rules, exact generated bytes, and BLAKE3 manifest. It does not prove model completeness, tool soundness, evidence success, whole-program correctness, hardware isolation, physical behavior, release eligibility, or automatic strengthening across mechanisms.

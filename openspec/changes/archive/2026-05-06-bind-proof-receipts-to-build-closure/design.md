# Design: Build closure receipt binding

## Context

The current proof rail receipts bind command/source hashes, provenance, configured verifier/toolchain identity, and the actual verifier binary hash. The remaining gap is build provenance: the binary may be correct while the Nix/toolchain/dependency closure that generated or selected it is not named in the receipt.

## Decisions

### Closure identity is a typed receipt-verifier obligation

`receipt_verifier` gains `verifier_build_closure`, `verifier_build_closure_digest`, and `verifier_build_closure_paths`. The identity is an operator-readable label such as `nix-tigerstyle-standards-build-closure/v1`. The digest is BLAKE3 over a deterministic manifest.

### Generated receipts hash checked closure manifests

When `verifier_build_closure_paths` is non-empty, `--execute-proof-rails` computes `proof-verifier-build-closure-blake3` from loaded source-root-relative files matching those paths. The digest algorithm sorts matches by path, hashes each file text with BLAKE3, then hashes canonical lines `<path>:<file-blake3>
`. If no manifest paths are configured, generated receipts fall back to the configured digest.

### Receipt-only checks require exact metadata lines

Receipt-only verification remains deterministic and read-only: it compares receipt lines against policy-exported closure identity/digest obligations and does not invoke Nix or inspect ambient builders.

## Risks

- The manifest must be generated by a trusted local Nix/build command outside the receipt parser. Mitigation: document the manifest contract and keep receipt validation deterministic.
- Self-referential package closure digests can be unstable if embedded directly in the source. Mitigation: bind to an explicit manifest file rather than the whole source-containing derivation path.

## Context

`cargo-octet/src/fingerprint.rs` keeps string/raw/byte/character literal contents and executable tokens after a quoted `//`. Before this cutover, `cargo-octet/src/object.rs` refused all source-backed Function Object construction because the former external Valence pin accepted only `octet-source-token-v1`; the reviewed new pin admits v2. The existing `octet.function-object.v1` object hash includes `normalization.algorithm` in the semantic ID and canonical payload. The v1 corpus receipt JSON has no independent normalization field: its `object_set_hash` binds the algorithm transitively through the objects. Consequently, the pre-archive OpenSpec `Positive v1 fixture replays cleanly` scenario could not remain true when default source emission switched to v2. H1/H2 approved the v2 selection and contract replacement; H3 guidance review and pinned native Cairn I7 also completed before supported OpenSpec promotion.

The OpenSpec change convention is `openspec/changes/<slug>/{.openspec.yaml,proposal.md,design.md,tasks.md,specs/<domain>/spec.md}`, with explicit `ADDED`/`REMOVED` delta sections here and exact scenario-to-V-task coverage. Cairn is a separate authored lifecycle (`.cairn/changes/<slug>/metadata.json`, `specs/<domain>/spec.md`, requirement IDs), not an alias for OpenSpec. A pinned CLI-authored spec-driven change aligned `.cairn/specs/valence-project-extraction/spec.md` without mutating historical Phase 2 receipts, then archived with explicitly supplied UTC date at `.cairn/archive/2026-10-02-valence-v2-source-identity-compatibility/`; OpenSpec separately promotes its own source-of-truth spec.

## Goals / Non-Goals

**Goals:** Distinct v2 normalization identity; source-backed named emit/check/corpus/supplement behavior; immutable readable v1 artifacts with honest mismatch against new v2 source; independently owner-reviewed, source-byte-bound internal/expanded v2 references and truthful selected Nix/fresh-build gates.

**Non-Goals:** Upstream Valence editing in this worktree; preserving v1 source replay as a default `match` by relabeling; automatic owner approval, pointer/marker/baseline rebinding, accepted evidence promotion; general compiler extraction, correctness, pure-cache, or cross-toolchain claims.

## Decisions

### 1. Keep upstream normalization identity authoritative

**Choice:** Candidate core/consumer/tests were developed under an explicitly unselected scratch Valence pin, never an approved production dependency or evidence. After the reviewed Valence API/commit admitted `octet-source-token-v2` and H1/H2 were recorded, Cargo, Cargo.lock, flake input/lock, and `standards/valence-core-cutover/{manifest.ncl,generated-manifest.json}` (including upstream `function_object.rs` BLAKE3) were selected together. The selected commit restores one source-backed constructor using `fingerprint::normalize_tokens` and the external typed constructor, preserving Function Object v1 schema only because that API explicitly supports v2 normalization under it.

**Covers:** Reviewed pin unlocks source-backed object emission; Quoted URL and literal changes alter v2 identity; Trivia leaves v2 identity stable; Macro lexical token boundaries change v2 identity.

**Obligation cross-check:** Emits an object with `normalization.algorithm="octet-source-token-v2"`; return-code/literal negative controls and trivia equality cover scanner identity; unreviewed pin continues to refuse construction; unresolved caveats keep claims false.

**Rationale:** The v1 label identifies old bytes; two meanings under one label would misstate the object hash. The independent fingerprint-marker v2 tag does not license reuse of Valence's v1 label.

**Alternative considered:** Keep emitting v1-labeled corrected tokens or silently update old receipts; rejected as false compatibility.

**Implementation:** Central `object.rs::function_object_for_source` consumes scanner span, full source, normalized tokens, dependency/macro facts and provenance; all selected source-backed callers use it. Artifact-only readers remain separate.

**Macro lexical boundary:** The candidate source lexer keeps compiler-visible token boundaries rather than replacing every punctuation boundary with a space: Rust `Punct::spacing()` distinguishes adjacent punctuation from punctuation separated by whitespace or ordinary comments, but whitespace beside a bracket group is still trivia. Numeric fractions/exponents/suffixes, raw identifiers and lifetimes, and attached raw-literal suffixes remain whole lexical tokens. Doc comments inside macro arguments are compiler-visible `#[doc = "..."]` attributes, not inert comment trivia; ordinary comments remain separators. Pinned-rustc proc-macro controls returned different results for each collided pair despite the prior identical source-token-v2 object hash. Macro-expansion `review-required` and pure-cache blockers constrain claims but do not excuse conflated reviewed source identities.

**Boundary cases:** Same tokens after trivia changes remain identical; literal contents or code after `"https://..."` cause different hashes. The shared scanner must include outer attributes attached across comments/blank lines, including multiline `#[unsafe(export_name =\n    "alpha"\n)]`: a pre-fix probe gave identical v2 hashes for `alpha` and `omega` even though rustc exported distinct symbols. Rustc also accepts a separate `pub` line, which pre-fix hashed as a private function. Balanced matching in the same-length code view must ignore brackets in literals/comments; split visibility/modifiers and stacked attributes belong to one item without swallowing markers or unrelated items. Export/visibility edits must change both the Function Object and reviewed function-address marker while trivia leaves the token object hash stable.

**Marker lexical boundary:** A pinned-rustc-valid block comment containing `// octet-object: b3:<matching>; review=R-stale; evidence=E-stale` previously produced a false reviewed `match`. Candidate scanning now checks each apparent marker's start against Rust comment/literal lexical state with one monotone per-file cursor, so even many reviewed functions cost O(source bytes) for this check rather than repeated source-prefix scans. Forged `// octet-fingerprint:` and `#[fingerprint(...)]` text inside block comments or raw literals cannot confer review either. The real marker above spaced/stacked attributes remains associated; explicit update after an inline `*/` inserts a new active marker but does not invent review metadata. The comment closer is excluded from source-token identity.

### 2. Separate historical artifact compatibility from current source replay

**Choice:** Freeze the checked-in v1 positive/negative receipt fixtures and existing expanded/internal v1 JSON. Keep old JSON artifact-only diff/pointer/bundle access. Under the v2 default, the historical positive v1 receipt parses but `object corpus check` returns `status="mismatch"` on `object_set_hash` against source; separately prepare `cargo-octet/tests/fixtures/object-corpus/source-token-v2/{src/lib.rs,positive-v2-receipt.json,candidate-source-manifest.json}` as **unselected diagnostic material**. That candidate manifest records exact source, receipt, and tested Valence module bytes with canonical repository URI plus repo-relative module path and approval `PENDING`; no machine-local checkout path is a durable review binding. It is not the future independently approved `reviewed-source-manifest.json` for fixed/internal/expanded refs. Selection requires owner review. No automatic v1 reconstruction, marker rewrite, pointer move, or approval is implied.

**Covers:** Historical v1 objects and receipts remain readable; Historical v1 source replay is stale under v2; Positive v2 fixture replays cleanly; V2 source drift changes object-set identity; V2 boundary tampering fails closed; Negative fixtures reject unsupported compatibility shapes.

**Obligation cross-check:** Distinguishes accepted *schema/read* from matching *source identity*; v1 negative receipt shape checks still return typed `invalid` with empty comparisons; v2 code/literal drift and boundary tamper fail with named comparison fields. The historical receipt, c9cdf page, markers and policy remain untouched.

**Rationale:** The v1 corpus receipt stores only an aggregate object-set hash, so a cross-version match is not meaningful. Versioned new evidence must not erase historical evidence.

**Alternative considered:** Add an implicit legacy scanner to make the old positive receipt match; rejected because it could reconstruct obsolete source identities during current checks. An owner-requested explicit read-only legacy replay mode would require a separate reviewed contract.

**Implementation:** New fixture and focused consumer tests; amend the promoted OpenSpec `Positive v1 fixture replays cleanly` clause only after approval. Leave old schema and fixture JSON intact.

**Boundary cases:** A v1 receipt with valid shape is not rejected simply for being v1; changing source must never accidentally pass. A future schema and malformed/missing-field fixtures remain invalid before source scanning.

### 3. Bind every source corpus rail to independently reviewed references

**Choice:** Reuse the EXISTING `object-corpus-gate`, `object-corpus-caveat-taxonomy-gate`, `object-corpus-fixture-freshness`, `fresh-build-object-corpus-determinism`, and `valence-object-evidence` check names. Require separately stored `source-token-v2/internal-corpus-receipt.json`, `source-token-v2/expanded-internal-corpus-receipt.json`, `source-token-v2/expanded-internal-corpus-caveat-taxonomy.json`, and `source-token-v2/reviewed-source-manifest.json`. Owner approval H2 is independent of current gate output. Until the manifest and each named reference are owner-reviewed and selected, their rails and aggregate fail closed; the old v1 JSON remains unchanged.

**Covers:** Bounded internal v2 corpus matches reviewed source-bound reference; Expanded v2 corpus and taxonomy match reviewed source-bound references; Fresh-build binaries match reviewed internal and expanded v2 references; Named fixture freshness rail compares reviewed v2 references; Selected child rails exercise real source-bound v2 behavior; Aggregate PASS requires all selected source-bound v2 rails.

**Obligation cross-check:** The manifest binds `normalization_algorithm=octet-source-token-v2`, exact standalone Valence revision and Octet version; the internal, expanded, and fixed quoted-URL corpus selections as SORTED repo-relative paths with BLAKE3 of EVERY selected source file's exact bytes; each reference receipt/taxonomy relative path and BLAKE3; and a separate owner review record identity. Admission compares all those stored facts with actual source and output before any PASS. A changed comment can preserve the canonical object hash while invalidating exact source-byte review: the gate still fails until a new owner decision. The owner record is independent of regeneration; a gate cannot mint approval. Required boundaries remain false and pure-cache blockers visible.

**Rationale:** Two receipts emitted by the same binary from the same changed sources can agree while losing reviewed freshness. An independently stored, reviewed expected receipt plus exact source-byte pin prevents a self-produced PASS. Inter-binary equality and fresh self-replay are useful SECONDARY determinism checks only after reviewed source/receipt identity is admitted.

**Alternative considered:** Treat two fresh receipts, a freshly emitted taxonomy, or just the tiny quoted-URL fixture as sufficient internal/expanded expected evidence; rejected because none binds the current Octet source set to an independently reviewed reference. Rename artifact-only tests or remove a failing child dependency; rejected as false PASS.

**Implementation:** H2 approval and an independent peer byte/path/hash audit selected a separate `reviewed-source-manifest.json` binding the immutable `PENDING` candidate snapshot, exact 37 source-byte hashes, four saved reference hashes, and the reviewed upstream Valence module. The candidate was not rebound, and later consumer-test edits are not owner-approved by H2. `tools/verify-reviewed-object-source.py` checks frozen manifest bytes, approval scope, every selected path/source/reference, false claim boundaries, and matching Cargo/Nix revision/module bytes before each existing object child, fresh-build, and aggregate rail runs. Distinct nonignored child tests exercise actual selected source emission/replay with stale-source/reference/receipt negatives; the fresh-build rail independently builds two binaries and compares BOTH internal and expanded receipts against the frozen references. The tamper matrix proves comment-only source drift, missing/altered references, false boundaries, missing approval, selector/path escape, and Cargo/Nix pin drift fail admission even when a token-derived object hash is stable. The existing zero-selection guard remains in place. `docs/contributor-guide.md` and `openspec/templates/tasks.md` require independent owner review for reference refresh. This admission is neither a signature nor correctness proof.

**Boundary cases:** A checked-in v2 reference lacking independent owner approval stays unselected; changed source trivia fails source-byte admission even when token hash is unchanged; the historical v1 receipts/taxonomy are never expected v2 bytes. Selected HIR/THIR/MIR remain fixture-bounded, and the c9cdf page attests only its old commit.

**Review trust limits:** The verifier executable and its expected digests are committed in the same PR-controlled repository. Its PASS proves internal consistency with its checked-in constants, not independent H2 authentication against a malicious edit to both; an out-of-PR reviewer MUST compare the candidate and reviewed manifests to externally frozen BLAKE3 `6d79a8b09c4e7dd20236f4a141c01d6c18b793df7aad93e8ee4ec1d7fb83b221` and `2f420d0464e67a8b6ae518e7215eefd1ba8afc47d1849c07afedf284f196da29`. The compiled producer includes `cargo-octet/src/valence_core_shim.rs` and `cargo-octet/src/object_core.rs`, outside the three H2-frozen Octet modules; H2 binds the 37 selected source bytes and four references plus observed source-backed scenarios, not every later producer edit or post-H2 consumer test change. Neither limit is repaired by self-replay or by treating the H2 decision as a signature.

## Deterministic Proof Plan

- **Source identity (V1–V3, V17):** V1 used `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_matches_fresh_reviewed_references_and_rejects_missing_receipt -- --exact --nocapture` plus direct source-backed CLI emission (`evidence/source-token-v2-emit.txt`). V2/V3 used `cargo test -p cargo-octet --test fingerprint_consumer object_v2_source_identity_preserves_url_tail_and_trivia -- --exact --nocapture` and direct temporary-source controls (`evidence/source-token-v2-url-drift.txt`, `evidence/source-token-v2-trivia.txt`). V17 used `cargo test -p cargo-octet --test fingerprint_consumer object_v2_macro_token_boundaries_change_identity_without_trivia_drift -- --exact --nocapture` (`evidence/macro-token-boundary-v2.txt`). These real selected-pin proofs cover normalization, literal/code drift, trivia equality, and compiler-visible doc-comment/macro token boundaries; no pre-selection source-backed PASS was accepted.
- **Historical and new receipt replay (V4–V9):** V4 used `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_compatibility_preserves_v1_artifact_read -- --nocapture` and a separate exact-Valence-checkout v1 golden test (`evidence/v1-artifact-read.txt`). V5 used `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_compatibility_historical_v1_is_stale_under_v2 -- --nocapture` (`evidence/v1-source-stale.txt`): historical v1 source replay mismatches on `object_set_hash` without invalidating readable v1 artifacts. V6–V8 used `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_compatibility_positive_v2_replays_and_rejects_source_and_boundary_drift -- --exact --nocapture` plus direct selected-source/temporary-tamper CLI controls (`evidence/v2-replay.txt`, `evidence/v2-drift.txt`, `evidence/v2-boundary-tamper.txt`): v2 replays as `match`, URL/code drift mismatches object set, and boundary tamper mismatches boundary. V9 used `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_compatibility_negative_fixtures_fail_closed -- --nocapture` and `cargo test -p cargo-octet --test fingerprint_consumer object_corpus_compatibility_source_selection_fixtures_fail_closed -- --nocapture` (`evidence/v1-negative-shapes.txt`): malformed/future/non-Rust shapes report typed `invalid`. No historical fixture was rewritten; exact command flags and inputs for each V-task remain in `tasks.md`.
- **Reviewed source-bound corpus:** Each existing named internal, expanded-caveat, and freshness rail ran after H2, with one transcript per rail under `evidence/`. Checks compared selected paths/source-byte BLAKE3 and current v2 receipt/taxonomy to separately saved reviewed references; missing/stale source/reference inputs fail despite two fresh identical outputs.
- **Independent build and aggregate:** Existing `fresh-build-object-corpus-determinism` and `valence-object-evidence` ran after H2, with separate transcripts under `evidence/`. Independently built binaries matched each other and both frozen internal/expanded references with false boundary claims; the aggregate named twelve child PASS lines after source admission. No substitute fixture gate was created.
- **Lifecycle and human review:** H1 changed-contract decision, H2 exact source/reference approval, H3 scoped contributor/task-template review, pinned native Cairn I7 creation/gates/sync/archive/strict validation, and pre-promotion strict OpenSpec validation are separately recorded in the change's evidence and tasks. No `git diff` source-text check is counted as behavioral verification, and no unchecked task or historical page becomes accepted evidence.

## Risks / Trade-offs

- Explicitly changing the promoted v1 source-replay `match` promise is a contract decision, not an incidental test update -> H1 approved the replacement delta; the supported OpenSpec archive separately promoted it after native Cairn I7.
- The formerly uncommitted Valence v2 API/schema required an unselected scratch pin during candidate work -> the reviewed API, H1/H2 and exact Cargo/Nix pins selected the package/rails and saved references; H3 and native Cairn I7 then completed before separate OpenSpec lifecycle promotion.
- Internal/expanded source bytes may change frequently -> fail the relevant selected rail until a fresh independently reviewed v2 reference and source manifest are approved; NEVER accept a self-generated expected receipt.
- New pin can invalidate Valence package readiness even if Cargo compiles -> update manifest revision/source/module hashes and Nix lock in lockstep; preserve non-proof boundaries.

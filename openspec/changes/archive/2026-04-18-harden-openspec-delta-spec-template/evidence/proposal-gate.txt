### 3. Ambiguities or omissions that should block design

**A. The MODIFIED requirement's `config.yaml` clause is underspecified relative to the proposal.**

The requirement says:

> `openspec/config.yaml` MUST contain one proposal rule that names `openspec/templates/proposal.md` and one proposal rule that names `openspec/templates/spec.md` for delta-spec authoring, plus one design rule that names `openspec/templates/design.md`.

This tells us *what keys to look for* but not the exact YAML shape or rule text. The ADDED requirements pin exact comment strings and exact headings — but this MODIFIED requirement leaves the config rule content as prose. That's probably fine for a guidance-wiring requirement (the config format is owned by OpenSpec upstream), but the scenario should be clear that verification checks for the *presence* of those rule names, not exact rule text.

**Verdict**: not blocking. The scenario's THEN clauses ("one proposal rule names ...") are testable by grepping the YAML. Design can pin the exact lines if needed.

**B. No explicit scenario for the "no extra second-level headings" negative condition.**

The first ADDED requirement says the template "MUST keep these exact second-level headings ... with no additional second-level headings." The scenario covers the positive path (maintainer can add requirements without inventing headings) but doesn't have a verification scenario that explicitly asserts the heading inventory is exactly three. 

**Verdict**: not blocking. The requirement text is normative and unambiguous. Design/tasks can extract the heading inventory as a deterministic artifact per the existing CLAUDE.md note about heading-inventory artifacts.

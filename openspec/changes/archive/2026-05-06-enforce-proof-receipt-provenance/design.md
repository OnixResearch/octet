## Context

The current verified proof rail accepts a committed receipt or an in-memory receipt generated by `--execute-proof-rails` when it has the configured pass signal and, for `blake3-command-and-source`, matching command/source hash lines. The next enforcement seam is typed provenance: receipt schema version, backend identity, runner identity, execution environment account, and trust-boundary account.

## Decisions

### 1. Policy-owned receipt provenance obligations

**Choice:** Add a `receipt_provenance` record to `ProofRail` with deterministic required values:

- `schema_version`
- `runner`
- `environment`
- `requires_backend`
- `requires_trust_boundary`

**Rationale:** Nickel remains the typed policy authoring surface; Rust consumes exported policy artifacts and validates receipt text. Booleans allow future rails to opt out of backend/trust-boundary lines while preserving a closed contract.

**Rejected:** Hardcode the lines only in Rust. That would make generated artifacts unable to explain the receipt contract to consumers.

### 2. Line-oriented receipt format

**Choice:** Require these lines when configured:

```text
proof-receipt-schema: <schema_version>
proof-backend: <rail.backend>
proof-runner: <runner>
proof-environment: <environment>
trust-boundary: <text>
```

**Rationale:** This extends the existing receipt format without inventing a parser or JSON schema migration. It remains deterministic and easy to generate from local commands.

### 3. No ambient environment dumps

**Choice:** Use a declared environment label such as `local-source-root` rather than hashing all process environment variables.

**Rationale:** Environment dumps can include secrets, usernames, timestamps, and host-specific noise. The provenance contract should identify the execution boundary, not leak ambient state.

## Risks / Trade-offs

- **Receipt churn:** Static fixture receipts need new lines. Mitigation: deterministic line format and CLI tests.
- **Overclaiming:** Provenance lines do not prove theorem semantics. Mitigation: docs and spec state this is local receipt provenance/trust-boundary enforcement only.
- **Future backend variety:** The record is intentionally small and closed now; future backends can extend it under a new OpenSpec.
